# Masar RTC — دليل إدارة الحوادث والاستجابة التشغيلية (Incident Runbook)

**الإصدار:** 1.0.0  
**التاريخ:** 14 أغسطس 2026  
**النطاق:** Web/PWA + Capacitor Mobile (Android/iOS) + Supabase Backend  
**الهدف:** توحيد إجراءات التعامل مع المشاكل التقنية والحرجة، وتقليل زمن الاستعادة (MTTR)، وحماية بيانات الطلاب والمتطوعين.

---

## 1. التفرقة بين الحادث التقني (Incident) والخطأ البرمجي العادي (Bug)

| المعيار | خطأ برمجي عادي (Bug) | حادث تقني حرج (Incident) |
|---|---|---|
| **الأثر** | خلل بصري، زر ثانوي لا يستجيب في شاشة غير حرجة، سلوك غير معتاد لمستخدم واحد لا يعطل العمل. | توقف تسجيل الدخول، تسريب بيانات، فشل جماعي في تسجيل الحضور، سقوط قاعدة البيانات، أو خطأ RLS يمنح صلاحيات خاطئة. |
| **الاستجابة** | يوثّق في تذكرة (Issue) ويجدول في الـ Sprint القادم. | إعلان حادث فوري (Incident declared)، وتشكيل غرفة عمليات، وتطبيق خطة طوارئ أو Rollback. |
| **زمن المعالجة** | أيام إلى أسابيع. | دقائق إلى ساعات معدودة حسب درجة الخطورة. |

---

## 2. مصفوفة مستويات الخطورة (Severity Levels)

| المستوى | الوصف | مثال | زمن البدء الأقصى (SLA) |
|---|---|---|---|
| **P0 — حرج جداً (Critical)** | توقف كامل للخدمة أو خطر أمني/تسريب بيانات شخصية. | عطل كامل في Google OAuth، اختراق RLS، فشل شامل في قاعدة البيانات. | استجابة فورية (أقل من 15 دقيقة) |
| **P1 — عالي (High)** | تعطل مسار جوهري دون بديل للمستخدمين. | فشل تسجيل حضور المحاضرات في جميع الفروع، توقف إصدار الشهادات. | أقل من 45 دقيقة |
| **P2 — متوسط (Medium)** | تعطل ميزة فرعية مع وجود بديل مؤقت. | بطء في تحديث المتصدرين، فشل إرسال إشعار محلي على إصدار معين من أندرويد. | أقل من 4 ساعات |
| **P3 — منخفض (Low)** | خلل ثانوي أو خطأ في الترجمة. | محاذاة نص في شاشة نادرة، خطأ كتابي في وصف شارة. | خلال الـ Sprint |

## 3. سلسلة التنبيه والمسؤوليات (Roles & Responsibilities)

عند إعلان حادث P0 أو P1، يتولى الفريق الأدوار التالية:

1. **قائد الحادث (Incident Commander - IC):**
   - مسؤول عن تنسيق القرارات وقيادة غرفة الطوارئ وتحديد خطة الإلغاء أو التراجع (Rollback).
2. **المهندس المسؤول (Lead Technical Responder):**
   - تشخيص السبب الجذري، فحص السجلات، وتجهيز الـ Hotfix أو الـ Rollback.
3. **مسؤول التواصل (Communications Lead):**
   - إبلاغ إدارة RTC والمشرفين بالوضع الحالي والوقت المتوقع للاستعادة (ETA) بصياغة واضحة دون مصطلحات تقنية معقدة.

## 4. إجراءات التخفيف السريع والـ Rollback

### 4.1 إيقاف ميزة أو تفعيل مفتاح الأمان (Kill Switch / Feature Flag)
- إذا كان العطل مرتبطاً بميزة حديثة (مثل Realtime أو ميزة إشعارات معينة):
  1. تعديل تفضيل الميزة أو الإعداد في الواجهة.
  2. نشر تحديث فوري للـ Web/PWA (يصل للمستخدمين فوراً عند التحديث).

### 4.2 إجراءات التراجع في الويب والـ PWA (Web Rollback)
1. إعادة نشر آخر Commit مستقر ومعتمد على منصة الاستضافة (Vercel / Pages).
2. تحديث نسخة الـ Service Worker في `sw.js` و`package.json` لإجبار المتصفحات على تفريغ الكاش القديم:
   ```js
   /* sw.js */
   var CACHE_NAME = 'rtc-v100.0.1-hotfix';
   ```
3. تنبيه المستخدمين عبر إشعار التطبيق للتحديث.

### 4.3 إجراءات التراجع في قاعدة البيانات (Database Rollback)
- **قاعدة ذهبية:** لا تنفذ `supabase db reset --linked` على قاعدة الإنتاج مطلقاً!
- للتراجع عن migration خاطئة:
  1. أنشئ migration جديدة تصحيحية (Forward-fix migration) تعيد المخطط أو الدالة السابقة:
     ```bash
     supabase/migrations/YYYYMMDDHHMMSS_revert_feature.sql
     ```
  2. اختبرها محلياً بعناية:
     ```bash
     npm test
     ```
  3. طبق الـ migration التصحيحية ثم أعد تحميل كاش PostgREST:
     ```sql
     NOTIFY pgrst, 'reload schema';
     ```

## 5. إجراءات إبطال التوكنات والأجهزة المشبوهة (Token & Device Revocation)

عند الاشتباه في اختراق حساب أو تسريب مفتاح وصول:

### 5.1 إبطال أجهزة الإشعارات للمستخدم
- يستطيع المستخدم أو النظام استدعاء دالة `disable_my_push_devices()` لتعطيل كافة التوكنات المسجلة له في جدول `push_devices`.

### 5.2 إبطال الجلسات عبر Supabase Auth
1. من خلال لوحة تحكم Supabase أو واجهة الإدارة:
   - الدخول إلى **Authentication** -> **Users**.
   - البحث عن المستخدم المعني والضغط على **Revoke Session / Sign Out User**.
2. لتغيير دور أو تجميد حساب مشبوه فوراً:
   ```sql
   SELECT public.set_user_status('USER_UUID'::uuid, 'suspended');
   ```

### 5.3 تسريب مفتاح الخدمة أو JWT Secret (حالة P0 القصوى)
1. الدخول فوراً إلى إعدادات مشروع Supabase -> **Project Settings** -> **API**.
2. توليد JWT Secret جديد (Rotate JWT Secret) مما يبطل جميع الجلسات القديمة فوراً.
3. تحديث مفاتيح الـ API في البيئات السحابية ومخدمات الـ CI.

## 6. ضوابط حماية البيانات الشخصية والسرية (PII & Secret Protection)

يمنع منعاً باتاً تضمين البيانات التالية في أي تقرير حادث، أو تذكرة GitHub، أو سجل عام:
- **كلمات المرور وتوكنات الدخول (Access/Refresh Tokens).**
- **مفاتيح الخدمات والأسرار (`supabase_service_role_key`, Google OAuth Client Secrets).**
- **أرقام الهواتف أو البريد الإلكتروني غير المقنّع للمستخدمين.**
- **محتوى الملاحظات الخاصة بالطلاب (`private_notes`).**
- **أرقام الشهادات أو التفاصيل الداخلية للمرشحين قبل اعتمادها.**
- **الاستعلامات وقصاصات السجلات التي تحوي نصوص SQL الخام مع بيانات مدخلة.**
